## 1. 论文究竟做了什么

CKKS 把复数向量编码为大整数系数的多项式，再加密。编码时先乘缩放因子 Δ，解码时除掉它。较大的 Δ 通常有利于数值精度，但乘法会使尺度相乘，需要 rescale；常规高精度乘法因此消耗较多模数预算。

论文的办法不是把 C++ 数值类型改成 `double`，而是把一个密文改为高、低两部分。用 `d=q_div` 表示分解基，重组关系为：

```text
原密文的表示 ≈ d × 高部分 + 低部分

两个重组量的乘积
  = d² × 高1×高2 + d × (高1×低2 + 低1×高2) + 低1×低2
```

Tensor2 保留前三项对应的三个密文乘积，舍去低×低项；重组后的理想结果相当于原始乘积先除以 d。随后 Relin2 控制重线性化误差，RS2 再除以本层乘法素数。只要低部分足够小，这种近似能在较少的模数消耗下维持高精度。

因此它不是精确整数乘法，也不是完全没有误差的“双倍精度”。低部分增长、加密噪声传播、舍入和解码误差都需要分析。表 3 的例子是初始尺度 `2^100`、连续八次平方；100 位尺度不等于最终承诺 100 位有效精度。

论文表 3 的 Mult2 参数为 `N=2^15`、`h=128`、两枚约 50 位 Base 素数、八枚约 60 位 Mult 素数、一枚约 40 位 Div 素数和一枚约 60 位 P 素数，最大 QP 约 680 位。精度约 `2^-81.8` 来自 1000 次执行的误差范数平均，不是每个输入、每把密钥均达到该值的保证。本项目按用户要求不以再做 1000 次为目标。

论文原页中的局部符号与归一化疑点，也不能照抄成代码修改理由：详见[原页核对记录](../../coordination/parameter-atlas-20260908/ROOT_PAPER_CROSSCHECK.md)。本项目采用的尺度关系需要与操作定义核对，而不是只匹配一条孤立的印刷公式。

## 3. 从参数到结果，实际执行了哪些步骤

```text
固定 profile：N / 有序 Q 与根 / b / 分布与模式
  → 建立 8 个逐层 family：各自 Q、P、QP、预计算表、context
  → 客户端抽取一个 h128 根秘钥，并生成公钥
  → 将同一个秘钥投影到各 family，分别生成其重线性化密钥
  → 确定性的高精度编码 + 一次公开密钥加密
  → 初始 DCP，得到高低密文对
  → 八轮 [Tensor2 → Relin2 → RS2 → 必要的下一 family 绑定]
  → 终端 RCB → 客户端解密与高精度解码
  → 与独立明文结果比较，并检查测量器自身误差
```

这里有两个不同的“基底”：family context 保存一套供升模和密钥切换使用的 Q；正在计算的高低密文对，在初始 DCP 后已移除了 Div 塔。说“保留 Div”必须指明是 family 模板，不能误说活动密文里一直有这枚塔。

| 平方轮次 | family 编号 | family Q 塔数（含 Div） | 轮前活动密文对塔数 | RS2 后活动塔数 |
| --- | --- | --- | --- | --- |
| 1 | 0 | 11 | 10 | 9 |
| 2 | 1 | 10 | 9 | 8 |
| 3 | 2 | 9 | 8 | 7 |
| 4 | 3 | 8 | 7 | 6 |
| 5 | 4 | 7 | 6 | 5 |
| 6 | 5 | 6 | 5 | 4 |
| 7 | 6 | 5 | 4 | 3 |
| 8 | 7 | 4 | 3 | 2 |

每轮消耗当前 family 的倒数第二枚 Mult 素数；下一 family 的定义保留 Div 作为最后一枚。终端活动结果只剩两枚 Base 素数。这里的下一 family 绑定不是新一次加密，也不是论文另一个实验中用于降误差的 DCP◦RCB 刷新。

每一步的作用分别是：

- **DCP**：在密文系数意义下分出商与余数，不是分别解密之后在明文侧分割。
- **Tensor2**：执行高×高及两个交叉乘积，舍弃低×低项；密文分量数从 2 变为 3。
- **Relin2**：把 3 分量重新线性化为 2 分量，同时通过高部分升模/分解保持误差补偿结构；不能简单地独立处理高、低部分来替代。
- **RS2**：对高部分以及重组量进行配套 rescale，以低部分补偿舍入差异；一次 Mult2 最终消耗一枚 Mult 素数，而不是因调用两次 rescale 就消耗两枚不同素数。
- **RCB 与解码**：重组高低密文，再使用精确尺度归一化。秘密操作只位于客户端，评价流程不靠中途解密来“修正”答案。

具体调用、表示、key-row 绑定和测试文件可从[项目参数与依赖图](../../coordination/parameter-atlas-20260908/PROJECT_PARAMETER_MAP.md)查起。

分工上，官方 OpenFHE 仍负责底层环/RNS/NTT 运算、公开密钥加密和密钥切换等；项目新增的是高低密文运算及状态绑定、固定 profile/同根 h128 适配、高精度客户端输入输出和独立检查路径。不是把 OpenFHE 全部重写，也没有为这份文档修改其随机数发生器。

## 4. 最重要的尺度区别

对连续平方，第 k 轮消耗的实际 Mult 素数记作 m_k。重组逻辑尺度满足：

```text
S_0 = 2^(2b)
S_(k+1) = S_k² / (d × m_k)
```

实际素数只是接近 2 的幂。因此精确尺度不会恰好每轮都回到 `2^(2b)`。OpenFHE FIXEDMANUAL 的兼容字段却在这里以 `2^b` 为因子处理，轮末 recorded scale 保持 `2^(2b)`。这两套数值不能互换。

根端的纯整数/高精度标量检查得到：八轮后，S100 的“精确尺度 / recorded scale − 1”约为 `3.6485e-4`；S116 约为 `1.5203e-5`。这**不是密文误差**，而是两种尺度的差值。当前客户端使用精确 receipt 路径；不能拿这个差值证明它解码错误。但以后若有人直接使用 recorded scale 作最终除数，就必须重新核对。

完整因子分解形式的八轮尺度在[静态检查结果](../../coordination/parameter-atlas-20260908/ROOT_STATIC_PARAMETER_CHECK.json)中；[执行记录](../../coordination/parameter-atlas-20260908/ROOT_EXECUTION_LEDGER.md)明确区分该检查与未执行的 FHE 实验。

### 编码/解码工作精度不是 S 的位数

项目客户端 `ClientReal` 使用 `cpp_dec_float<100>`，这是 **100 位十进制工作精度**，不是论文的 100 位二进制尺度。变换内部另用 160 位与 220 位十进制工作类型，各自生成高精度根表，不把 OpenFHE 的 binary64 槽缓存当成高精度输入。

实际路径是高精度逆变换、乘精确尺度、稳定整数舍入、精确转入官方大整数/RNS，再调用官方 scheme 的公开加密；解密走官方 scheme 的 `Poly*` 路径，取居中整数系数后用精确尺度和高精度正变换还原槽位。这绕过普通高层 Plaintext/binary64 编解码路径，但没有绕过官方 PKE 或中途用明文替代计算。

稳定舍入不仅比较两个工作精度得到的整数，还拒绝过于接近半整数或超出支持范围的输入。辅助 `PaperRound` 定义最近整数、半整数向下；公开编码路径的保守检查可能先拒绝这类边界，不能声称接受所有可能的实数输入。解码时两种工作精度的各槽实/虚部分歧不得超过 `2^-120`。

两种精度结果一致，只说明这一检查下数值稳定，**不证明共同采用的槽顺序或公式一定正确**；还需要独立 oracle/变换检查。这里的 `2^-120` 是客户端一致性门槛，与最终加密计算的 `2^-80` 验收门槛不是一回事。固定项目源码锚点：`high_precision_client_io.h:23–24`，`high_precision_client_io.cpp:54–57,333–495,606–635,684–755`。

## 5. 随机性到底从哪里来

```text
系统随机源等种子输入
  → 默认 BLAKE2Xb 伪随机引擎（有状态，按线程组织）
  → 分布适配器：均匀 / 二元 / 三元 / 离散 Gaussian
  → 系数多项式或各塔均匀元素
  → 秘钥、公钥、payload 加密、重线性化密钥

同一随机流还可能被以下操作消耗：
素性校验、辅助素数/单位根生成、临时私钥包装对象的 key tag 生成
```

### 不能遗漏的六个区别

1. **秘钥与加密临时量不同。** 上游常规 sparse KeyGen 的硬编码重量是 192；本项目用显式适配器抽取 h128。公开密钥加密的 v 在非 GAUSSIAN 模式下仍是默认稠密三元，不能由 h128 推成 v 也稀疏。
2. **h128 不等于任意独立符号。** 当前固定源码的稀疏三元采样还限制正系数数目为 63、64 或 65；内部拒绝抽样可重复。一次 API 调用不代表一次固定长度 PRNG 消耗。
3. **小多项式与均匀大环元素不同。** Gaussian/ternary DCRT 构造先抽一个有符号系数向量，再映射到所有 RNS 塔；均匀 DCRT 构造则在各塔下分别采样。把前者写成“每塔独立 Gaussian”会破坏对噪声的理解。
4. **同根秘钥不等于复用所有随机材料。** 各 family 的秘密系数是原根秘钥的确定性投影，但 evaluation key 的随机 a/e 会重新生成。临时 key tag 的随机生成也不等于重新抽了一把秘钥。
5. **固定公开参数不等于过程无随机数。** 辅助素数检查和 primitive-root 搜索会消耗 PRNG；单位根随后规范化为最小 primitive root。最终相同的根，不表示生成过程没有随机调用。
6. **同一 seed 不自动保证跨平台重复。** 线程、调用顺序、拒绝次数、标准库分布实现和公开校验调用都会影响随机流。不要记录真实私钥或种子来充当普通日报证据，更不能把可预测测试随机性用于生产。

本项目公钥构造采用 `(a*s+e_pk, -a)`，公开加密后解密得到的代数关系为：

```text
m + e_pk*v + e0 + e1*s        （此处 noiseScale = 1）
```

所以 h、v、σ 分别进入不同的误差项；不能只调一个“噪声参数”就假定其他条件不变。这一关系是由源码公式推导，不是本次测得的误差上界。[完整随机性源码图](../../coordination/parameter-atlas-20260908/ROOT_RANDOMNESS_MAP.md)提供各条路径的固定文件和行范围。

一次 packed payload 包含 16384 个槽，不意味着做了 16384 次独立密钥实验。各槽来自同一次环加密/计算及其噪声，不能把槽数直接当成独立重复执行的样本数。

### 配置 σ 与实际 sampler 状态的条件性差异

当前上下文名义 σ 是 `3.19f`，而独立 DGG 构造器默认是 1.0。上游 HYBRID 密钥生成循环使用 OpenMP `private(dgg)`；按照 C++ OpenMP 私有化规则，私有对象是默认构造，而不是从外层配置对象复制。因此在启用该 pragma 的构建中，循环内有效状态需要单独分析。

这是一项固定源码加语言规则的条件性推论，不是对已有二进制实测得到“σ=1.0”，也不是原 S100 失败的已证实原因。仅设置 OMP_NUM_THREADS=1 仍不等于关闭 OpenMP 私有化。详见[一手 OpenMP 规则核对](../../coordination/parameter-atlas-20260908/OPENMP_PARAMETER_SEMANTICS.md)。未经单独验证，不因此改采样器或降低误差分布。

| N / slots | cyclotomic order、素数同余、单位根/NTT 表、向量尺寸、packing 顺序、全部密钥和 context、编码与 observer | 不能直接沿用精度、性能或安全结论。 |

| Div d | 分解/升模/重组、Relin2 补偿、每轮尺度、低部分误差分析、终端解码 | 旧数值接受条件需重新论证。 |
| P / 分区数 | 辅助基大小、mod-up/mod-down 表、evaluation-key A/B 维度、性能和总 QP | 密钥大小、噪声与安全估计不可直接继承。 |
| S 或 b | 编码整数、兼容字段、精确 receipt、Q 的容量、所有尺度 oracle | 不能仅改 metadata 声称提高了精度。 |
| 深度 / family 数 | Mult 素数数目、8 轮硬编码假设、每层密钥、收据链、终端层/基底、结果格式 | 所有“完成八轮”的证据需按新任务重新定界。 |
| h / σ / v 分布 | 实际采样调用、公钥与评价密钥、误差项、采样器分支、安全分析 | 旧钥不会因修改配置而变；不能直接继承安全或精度声明。 |
| 编码/解码精度 | 变换精度、舍入分歧检测、整数 lift、observer 独立性 | 原测量器的可信范围和误差预算需重审。 |
| 输入范围 | 确定性生成式、理想结果、幅度/绝对/相对误差解释、验收标签 | 换输入后的 PASS 不是原压力输入的修复。 |
| OpenMP / PRNG / 依赖 pin | 真实构建分支、线程归属、sampler 私有对象、调度和种子政策、缓存来源 | 不保证跨平台同样随机样本；历史记录仍只对应原构建。 |

完整的“设置点→消费点→受影响测试文件”矩阵见[项目参数映射](../../coordination/parameter-atlas-20260908/PROJECT_PARAMETER_MAP.md)。这些是影响分析，不是允许现在把所有参数都改一遍。

## 7. 后续怎样用文档找问题

先明确出问题的层次，再选择最小、能区分原因的检查。不要从“精度没达到”直接跳到“算法错误”。

| 症状 | 优先核对 | 不应直接得出的结论 |
| --- | --- | --- |
| fresh 解密就有较大误差 | 编码量化、公开加密误差项、实际 v/σ、正确尺度、测量器 | 不等于 Tensor2/Relin2 有错。 |
| 首次乘法出现数量级偏差 | 是否漏掉 d、metadata 与逻辑 S 混用、模数/槽顺序 | 不能只把输出乘个常数“校正”后宣布通过。 |
| 后几轮才恶化 | 输入幅度导致的误差传播、低部分增长、本层 q 与精确尺度、是否接近模数绕回 | 不自动证明某一轮源代码有错误。 |
| key/basis/receipt 校验失败 | 对象所属 family、根与塔顺序、对应 key row、生命周期 | 不能删掉校验让程序继续。 |
| Linux/Windows 有差异 | 固定依赖、实际构建条件、随机样本、线程、数值实现与 observer | 未配对的独立噪声样本不应要求逐比特相同。 |
| 宣称 PASS 但口径不明 | 是否真的执行加密和全槽比较、阈值是否改动、范数/样本数/commit、是否只跑 controls | 结构测试通过不等于完整精度通过。 |

文档完成后，先从实际源码差异或可检验假设中选择一个诊断切片。需要编译或加密实验时放到 Windows/GitHub runner；本轮导读没有启动任何此类实验，也不联系作者。
