## 2. Distribution adapters and DCRT representation

### Ternary: distinguish dense from fixed weight

Observed: `O:src/core/include/math/ternaryuniformgenerator-impl.h:50–64` and `103–108` define/use a uniform integer distribution over `{-1,0,+1}` when `h == 0`. This is **dense independent-coordinate ternary under the PRNG/distribution model**, with random Hamming weight, not an all-zero request.

Observed: sparse paths are `GenerateVector:67–99` and `GenerateIntVector:111–143`. They clamp `h > size` to `size`, repeatedly choose unoccupied indices uniformly in `[0,size-1]`, and assign signs through `BinaryUniformGeneratorImpl::GenerateInteger`. That binary helper uses `std::bernoulli_distribution(0.5)` and `GetPRNG` at `O:src/core/include/math/binaryuniformgenerator-impl.h:48–53`. The entire candidate is retried until positive count lies between integer `h/2-1` and `h/2+1`.

**Inferred for the in-scope h = 128, N >= 128 branch:** an accepted candidate has 128 nonzero coefficients and 63, 64, or 65 positive entries. Given ideal uniform draws, it is a distribution conditioned on that sign-count interval, not fixed weight with unrestricted independent signs and not forced exactly 64/64. Duplicate position draws and rejected sign-count candidates consume additional randomness. “One call to the h128 sampler” allows internal retries.

**Limit:** do not turn the arbitrary `uint32_t h` API into a claim that every small/edge value has the same contract. The exact while guard uses unsigned arithmetic and an initially zero positive count; its boundary values need their own semantic review. No small-h experiment or proposed sampler fix was performed in this assignment.

### Uniform and DCRT constructors

- **Observed uniform adapter:** `O:src/core/include/math/discreteuniformgenerator-impl.h:46–97`, `SetModulus`, `GenerateInteger`, and `GenerateVector`: forms unsigned 32-bit chunks with a bounded high chunk and rejects candidates `>= modulus`; accepts `[0,q-1]`. This is rejection sampling, not unconditional modulo reduction of a fixed-width word. Modulus zero is rejected in `GenerateInteger`. Changing `q` can change chunks and rejection/draw counts.
- **Observed DCRT Gaussian:** `O:src/core/include/lattice/hal/default/dcrtpoly-impl.h:125–149`: samples **one** signed length-N vector via `dgg.GenerateIntVector`, maps the same signed values into every modulus, marks coefficient format, then converts to requested format. There is a special per-tower modulo branch if sigma exceeds that tower's modulus. Do not describe independent Gaussian coefficients in different towers.
- **Observed DCRT ternary:** same file `177–192`: **one** `tug.GenerateIntVector(N,h)`, same signed vector mapped across all towers, then coefficient-to-requested format. The public declaration `O:src/core/include/lattice/hal/default/dcrtpoly.h:111` supplies default `h = 0`.
- **Observed DCRT uniform:** impl `152–159`: for each tower, calls `dug.GenerateVector(N,q_i)`, then stores directly in requested `m_format`; it does not sample one small signed vector and replicate it. **Inferred:** with pairwise coprime moduli and ideal independent uniform coordinate draws, CRT gives uniform residues modulo the product; an invertible NTT preserves uniformity even when sampled directly in evaluation coordinates.
- **Observed DCRT binary:** impl `162–174`: creates a coefficient polynomial once, switches modulus for other towers, then converts each to requested format. This is consistent across towers like a small coefficient sample, unlike full-modulus uniform sampling.

The relevant Gaussian/ternary DCRT constructor loops have no outer sampling `omp parallel for`. Their caller may already be inside an OpenMP loop. A polynomial's sampled domain (coefficients vs slots vs NTT coordinates) and its RNS representation must be stated separately.

### OpenMP `private(dgg)` is a material effective-sigma branch

**Observed:** HYBRID private→private code copies context DGG at `keyswitch-hybrid.cpp:93`, then declares it `private(dug, dgg)` in the OpenMP loop at `98`. The private→public version uses `private(dgg,tug)` at `156`. BV has the same pattern at `75`, `89`, `132`, `146`, `189`, and `207`. The default DGG constructor argument is 1.0 (`discretegaussiangenerator.h:93`).

**Inferred from OpenMP C++ privatization semantics:** when these pragmas are compiled and active, private class objects are default constructed rather than copy initialized from the outer context DGG. Thus these loop-local DGGs start with sigma 1.0, even when the visible context reports 3.19f; with pragmas compiled out, the outer copied DGG is used. A one-worker OpenMP team still executes the private-object semantics, so `OMP_NUM_THREADS=1` is not equivalent to a non-OpenMP build for this question.

Primary semantics reference: [OpenMP 5.2 §5.3, List Item Privatization](https://www.openmp.org/spec-html/5.2/openmpse25.html#x68-700005.3). The root agent independently retrieved and supplied the relevant rule: a new C++ private item is initialized as a locally declared variable without an initializer, and a class item requires an accessible unambiguous default constructor. This worker did not perform a network request; the root agent owns the web-source receipt.

## 6. Final atlas cross-check checklist

### Root follow-up: key-tag generation is another PRNG consumer

After the independent worker completed this map, root inspected `O:src/pke/include/key/privatekey.h:55–97`, `key/key.h:53–66`, and `cryptoobject.h:51–78`. `PrivateKeyImpl(context)` calls `GenerateUniqueKeyID()`, which performs four `std::uniform_int_distribution<uint32_t>` invocations using the same `PseudoRandomNumberGenerator::GetPRNG()` and formats them into a 32-character hexadecimal identifier. This is an identifier, not a secret-polynomial sample or a guaranteed collision-free ID. Copy/move constructors preserve the existing tag instead. The exact number of engine invocations behind a distribution call is not asserted as a cross-platform contract.

Consequently the seven projected-family private-key wrappers in `P:src/repeated_mult2.cpp:373–375` consume tag-generation randomness before their tags are replaced with the deterministic family tag (`rootTag + "-mult2-family-" + family`, line355), not with the identical root tag. This resolves the explicitly upstream-unknown constructor boundary in `PROJECT_PARAMETER_MAP.md`. It does not mean that those wrappers sample seven new secret polynomials. Also, each ordinary `EvalMultKeyGen` creates `PrivateKeyImpl(context)` for `s²` at `O:src/pke/lib/schemebase/base-leveledshe.cpp:139`, so its temporary wrapper generates a tag too even though the secret is squared deterministically. The eight-family setup thus includes eight such extra tag-generating constructors, in addition to its explicit root and seven projected wrappers. This is a source-call count, not an exact engine-word count or a new-secret count. Root performed source inspection only, not key construction or RNG execution.

### Root follow-up: fixed Q does not make auxiliary-parameter construction RNG-free

Root additionally read `O:src/pke/lib/schemerns/rns-cryptoparameters.cpp:44–175`, `ckksrns-cryptoparameters.cpp:185–188`, and `O:src/core/include/math/nbtheory-impl.h:63–129,183–230,261–394`. Project `MakeFamily` invokes `PrecomputeCRTTables` before obtaining the context; its frozen Q does not skip upstream HYBRID P generation. That path computes partition size `ceil(sizeQ/numPartQ)`, sizes P using `ceil(max_partition_bits/auxBits)`, obtains the CKKS prime step `2*N`, then calls `FirstPrime`, `PreviousPrime` (skipping primes already in Q), and `RootOfUnity`.

The prime search advances along a fixed arithmetic progression but uses randomized Miller–Rabin witnesses to accept candidates. `RootOfUnity` calls `FindGenerator`, which factorizes `q-1` using primality tests and Pollard–Rho, and draws trial generators through the same `RNG`/PRNG accessor. It then cycles through coprime powers and selects the minimum primitive root. Thus the returned root is canonical for valid prime/order inputs even though its construction consumes random words; do not equate a fixed public output with a randomness-free computation. No prime, factorization, root search, or precomputation was executed by root here.
