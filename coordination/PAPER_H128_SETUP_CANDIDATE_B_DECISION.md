# Candidate B decision: one fixed-Q h=128 client keypair adapter

## Recommendation and authority

Recommend advancing **one project-owned, single-party client setup adapter**, provisionally named `CreateFixedQH128ClientKeyPair(context)`: accept an already finalized CKKS context and return fresh official OpenFHE private/public key objects. Do not build contexts, provide a generic key factory, use the multiparty debugging helper, or copy RLWE algorithms. This is a proposed public seam, **not upstream KeyGen endorsement or user-confirmed implementation authority**.
Source-only audit on 2026-09-04; branch `codex/repeated-mult2-01`, starting HEAD `05c8cd873070144b0c74b0f0c5cde93420924d46`, initially clean; concurrent unrelated coordination files are preserved. No build, crypto, test, CI, cache mutation or external dispatch occurred.

## The selected construction — proposed, not executed

1. Check the **actual supplied context and its attached parameters**, not a discarded requested parameter object, against every precondition below. Contexts may be reused read-only across trials; key identities must be fresh.
2. Construct one official ternary DCRT polynomial on that context's full ordered Q in EVALUATION format with explicit h=128; check copied coefficient towers for the same signed ternary pattern and exactly 128 nonzeros. The constructor samples once and represents that pattern in every tower. Record the sampler's 63–65 positive-sign condition without logging secret coefficients. [constructor](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/core/include/lattice/hal/default/dcrtpoly.h#L99-L112); [shared coefficient pattern](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/core/include/lattice/hal/default/dcrtpoly-impl.h#L178-L193); [h and sign rejection](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/core/include/math/ternaryuniformgenerator-impl.h#L103-L143).
3. Construct a **new** PrivateKeyImpl in this same context, set its private element once, and require a nonempty tag not already used by the task or present in the EvalMult cache. Invoke the public scheme `EncryptZeroCore(sk)` on that context; require a nonnull two-element result, both on exact Q in EVALUATION format. [fresh tag](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/key/privatekey.h#L55-L83); [private element](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/key/privatekey.h#L127-L149); [public zero-encryption wrapper](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/schemebase/base-scheme.h#L227-L239); [public cache observation](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/cryptocontext.h#L1068-L1079).
4. Construct PublicKeyImpl with that **same context and tag**, install the returned two elements in their original order, and verify both actual key getters' context identity/tag. Publish the complete pair only after checks; do not expose a half-built key or replace an existing key's secret. ## Observed source and mathematical consequence

- PKE enablement installs PKECKKSRNS; its class inherits PKERNS without overriding EncryptZeroCore, whose override is declared public. The scheme wrapper checks PKE enablement and nonnull key only, passing a null basis override. It does **not** validate context identity, h, tag or ordered basis. [enablement](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/scheme/ckksrns/ckksrns-scheme.cpp#L42-L58); [CKKS class](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/scheme/ckksrns/ckksrns-pke.h#L45-L75); [RNS override](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/schemerns/rns-pke.h#L109-L119); [wrapper](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/schemebase/base-scheme.h#L227-L239). Even the context's ValidateKey checks only null/context identity. [validation](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/cryptocontext.h#L319-L333).
- Ordinary KeyGen samples its secret on GetParamsPK(); SPARSE_TERNARY requests literal h=192, then samples a and e and returns (ns·e−a·s,a), dropping extra secret towers if needed and aligning tags. Candidate B instead supplies h=128 and uses the private-key RNS zero-encryption path, which defaults to GetElementParams() and returns (a·s+ns·e,−a). Both take their Gaussian generator and ns from the same crypto-parameter object. [ordinary KeyGen](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/schemebase/base-pke.cpp#L45-L98); [candidate primitive](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/schemerns/rns-pke.cpp#L111-L146).
- **Derived algebra, ns=1:** if a′=−a, Candidate B's pair is (e−a′·s,a′), hence pk₀+pk₁·s=e in R_Q: the ordinary public-key relation for the supplied s. There is no sign fix, component swap or additional encryption required. This is not bitwise replay of KeyGen, not equality to its h=192 secret distribution, and not a security/HEaaN/noise-equivalence result; neither a SPARSE_TERNARY declaration nor HEStd_NotSet supplies security evidence.
- Official public-key encryption consumes these two entries as (m+pk₀·v+e₀,pk₁·v+e₁), so the decryption relation is m+e·v+e₀+e₁·s. For non-Gaussian SecretKeyDist its ephemeral v uses the **default** ternary constructor, not h=128; do not change that primitive. [Encrypt](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/schemerns/rns-pke.cpp#L56-L69); [public-key core](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/schemerns/rns-pke.cpp#L148-L196).

## Exact initial profile and rejection conditions

These are adapter contract requirements, not evidence that an arbitrary manually constructed context satisfies them.

| Required actual state | Reject / do not silently repair |
| --- | --- |
| Nonnull CKKS context, CryptoParametersCKKSRNS and CKKS scheme; getSchemeId() = CKKSRNS_SCHEME | Null/wrong scheme or parameters, INVALID_SCHEME, inspection of requested rather than returned objects. Scheme ID defaults INVALID in the public context constructors. |
| Power-of-two N≥128; nonempty valid ordered Q, matching cyclotomic order/N/each modulus and root | N<128 (the sampler clamps h), inconsistent or reordered basis, comparison by total modulus/length alone. Paper acceptance separately requires N=32768. |
| STANDARD encryption, FIXEDMANUAL scaling, HYBRID switching; **PREMode=NOT_SET**, noiseScale=1; declared SPARSE_TERNARY; preserved finite positive Gaussian σ | EXTENDED, any other scaling/switching/PRE profile, ns≠1, GAUSSIAN/UNIFORM_TERNARY/SPARSE_ENCAPSULATED declarations, parameter relabeling or replacement of the supplied Gaussian generator. No security/noise mode is silently disabled. |
| **GetParamsPK() is nonnull and actually equals context Q**, not QP/Qr | STANDARD alone is insufficient: HYBRID and PREMode≠NOT_SET select QP before the encryption-technique branch. This first adapter does not relax PREMode or synthesize extended public keys. |
| PKE and actual HYBRID/LEVELEDSHE implementation initialized before publication; Q/P/QP tables already generated for this exact context | Bare Enable(KEYSWITCH), null P/QP, wrong Q-prefix/P/partition shape, invalid digits or subsequently altered tables. The adapter does not call precompute/setters on a live context. |
| Fresh SK/PK objects; same exact context and nonempty new tag; SK and both PK elements EVALUATION/full Q; PK length exactly two | Reused/colliding tag, mixed contexts, altered secret after public/eval-key generation, family copies mislabeled as fresh independent keys. |

## Metadata, lifecycle and basis-family boundary

- Keys own context/tag and polynomial elements, **not ciphertext slots, level, encoding type or logical scale**. This setup operation returns no Ciphertext or stale Plaintext. The ordinary context Encrypt wrapper copies those fields from Plaintext; any future high-precision Element-based I/O must establish them separately. Do not invent a key scale or freeze an I/O scale type here. [key state](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/key/publickey.h#L58-L71); [base state](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/cryptoobject.h#L55-L100); [ciphertext metadata](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/include/cryptocontext.h#L1250-L1266).
- Generate ordinary EvalMult keys from the **returned SK** only. The source forms s² and switches to that same s; HYBRID reads the supplied secret, extends it to QP and sets the destination key tag. It does not run normal KeyGen to replace h128 by h192. This supports the route, not specialized Relin2 or repeated-Mult2 correctness. [s² generator](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/schemebase/base-leveledshe.cpp#L135-L162); [HYBRID key generation](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/keyswitch/keyswitch-hybrid.cpp#L46-L129); [tag assignment](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/schemebase/base-scheme.cpp#L57-L71).
- Immutability is a project ownership contract: public OpenFHE setters remain mutable. Freeze actual context/basis/parameters/key identity before exposure, never change them under existing ciphertexts/keys, and validate snapshots at the relevant public boundaries. No claim of transitive C++ immutability follows from a const shared_ptr.
- **1000-trial ownership:** EvalMultKeyGen/KeysGen skip an existing tag and the static map retains each new entry. Releasing local key handles is not a cache-lifetime policy. Use bounded trial/family lifetimes and, after their dependants finish, erase only this task's owned **nonempty tags** via ClearEvalMultKeys(tag). Never clear all or clear by a shared context. The string overload body only find/erases that tag; unlike a header comment, it does not implement empty-string clear-all. No cache was changed here. [static map](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/cryptocontext.cpp#L45-L46); [generation and exact clearing bodies](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/cryptocontext.cpp#L87-L129).
- Per trial, a basis family must share one sampled **integer secret**, projected/re-embedded into each already-frozen basis with fresh per-family key objects/tags and regenerated matching public/eval keys. Repeatedly calling this fresh-sampling adapter independently for each basis does not create that family. Same N, ordered residues, per-family P/QP/partition tables and level-relative metadata remain the family owner's obligations; no arbitrary retag/routing equivalence is certified. For L towers the precompute digit check is L>ceil(L/d)·(d−1); d=11 is invalid for L≤10, so shorter bases cannot blindly retain paper dnum11. [basis-specific digit guard](https://github.com/openfheorg/openfhe-development/blob/df495ba2e91739a6dc8f1de254fc5a41155ce504/src/pke/lib/schemerns/rns-cryptoparameters.cpp#L62-L90).
- Root reports the incoming shape-only probe explicitly passes PREMode INDCPA; this task did not reread that probe C++. The verified paramsPK branch means such a context is **outside this Q-only adapter profile**. Future paper-setup/I/O construction must reconcile PREMode before creating/finalizing contexts; do not mutate an interned context or declare a Relin-only shape probe wrong merely because it has not served public I/O.

## Proposed smallest public-seam acceptance — prose only, not frozen tests

1. After user confirmation, first exercise the proposed setup operation on one **N=256 diagnostic** fixed-Q context matching the profile; Pro must freeze the exact prime/root list, σ, digit/P settings and ordinary smoke-encoding scale in that contract before RED. Observe actual returned keys through public getters: exact h128/ternarity/common signed support, 63–65 positive signs, two PK elements, complete Q identity/format, same context/tag. Verify no supplied context/table snapshot changed. Keep secret coefficients out of logs. Ordinary SPARSE_TERNARY KeyGen at this N requests h192 and cannot serve as a passing h128 substitute.
2. Use those returned keys with official public Encrypt/Decrypt and newly generated EvalMult key, not a schoolbook secret oracle or the multiparty helper. Use a small full-packed dyadic roundtrip and ordinary relinearized square. Pro must freeze the valid diagnostic Q, input scale, decryption mode and explicit numerical tolerance before RED, preserving the configured noise generator. This is a key-compatibility smoke, not an 80-bit I/O or paper-precision gate.
3. Public-seam negative cases: null/wrong-ID context, N64, PRE INDCPA, EXTENDED, non-FIXEDMANUAL, non-HYBRID, ns≠1, wrong secret-distribution declaration, and missing/invalid context precomputation. Reject before publishing keys; no fallback h192, metadata patch-up or shared-context mutation. The genuine initial missing behavior is this h128 client-setup seam, not a staged current-second-call rejection.
4. Inspect that the adapter actually delegates sampling/zero encryption to the cited public primitives; structural/roundtrip tests alone are not security evidence. Add a second fresh instance to check isolation and owned-tag cleanup without erasing an unrelated retained tag. Hosted compile/runtime, matching family integration and paper N32768 validation remain later evidence; no rotations, serialization subsystem or security theorem is added.

## Remaining decisions, not new completion gates

Main/user must confirm the public setup seam and its initial diagnostic contract, accept this project-owned public-primitive composition rather than demand upstream KeyGen endorsement, and approve the fixed-Q/PRE/ownership boundary shared with the pending I/O and basis-family designs. The core pair construction needs no additional source file to justify this proposal, but still needs real compiled/cryptographic validation.
The existing `PAPER_H128_DISTRIBUTION_REQUIREMENT.md` treats unverified HEaaN sign-law equality as a comparison limitation, not a new gate; `REPEATED_MULT2_ACTUAL_RETURN_DISPOSITION.md` keeps h128 mandatory for paper setup, **not** a prerequisite to a permitted low-N semantic second-operation diagnostic. This note adopts neither incoming candidate nor production code and does not claim paper completion.
