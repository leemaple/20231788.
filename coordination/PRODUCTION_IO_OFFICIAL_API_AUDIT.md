## 1. Where standard CKKS narrows precision

- **O:** Both MakeCKKSPackedPlaintext overloads accept double or complex<double>; CKKSPackedEncoding stores a private complex<double> vector and returns that type. The high-level helper selects a double scale and calls Encode. REAL mode explicitly zeros the imaginary input. [Inputs][input], [helper][make], [cache/REAL conversion][cache], [getters][getter].
- **O:** Encode copies that vector and calls FFTSpecialInv. Both the public transform signatures and roots/twiddle calculations are double based. NATIVEINT=128 still uses double mantissas and a 52-bit precision constant; it is not a multiprecision slot encoder. The 64-bit branch also rounds scalingFactor through llround before conversion to its native scale integer. [Encode/native branches][encode], [scale conversion][encscale], [DFT API][dftpublic], [roots][dftroots].
- **O:** Decode centers native/big coefficients, then calls ConvertToDouble and stores complex<double>; changing a return type after these conversions cannot restore lost input bits. FIXEDMANUAL's Poly normalization uses p and noiseScaleDeg; the one-tower Native branch uses 2^-p, not an arbitrary exact scale descriptor. [Decode][decode].
- **O:** cc->Decrypt always invokes CKKS Decode after the scheme returns coefficients. Decode zeroes its raw Poly/NativePoly coefficient storage. Thus “ordinary Decrypt, then read its polynomial” is not a lossless escape hatch. [Context wrapper][ccdecrypt], [coefficient clearing][decode].
- **I:** A high-precision client must avoid binary64 at input, twiddle generation, integer/scale conversion and final output. A larger Q, native integer width, or printed decimal precision alone cannot remove the above narrowing. Multiprecision slots remain approximate numerical values, not exact algebraic values merely because the scale is rational.

## 2. Official raw decryption, not test-owned secret arithmetic

- **O:** GetScheme is public. SchemeBase has public Decrypt overloads for Poly* and NativePoly*, plus DecryptCore returning Element (DCRTPoly here). PKE enablement installs PKECKKSRNS, whose overrides are public. [Getter][getscheme], [overloads/core][schemeio], [installation][pkedispatch], [override declarations][pkeoverride].
- **O:** PKECKKSRNS::Decrypt(..., Poly*) uses the official DecryptCore, conditionally adds polynomial noise when NOISE_FLOODING_DECRYPT and EXEC_EVALUATION are selected, changes to COEFFICIENT, then converts one tower to Poly or CRT-interpolates multiple towers. It returns before slot decoding and before any coefficient ConvertToDouble. NativePoly* requires exactly one tower; Poly* also handles one tower. [Full overrides][ckksdecrypt].
- **O:** Scheme DecryptCore directly calls the RNS core; it has null checks but does **not** perform the CKKS override's flooding. Its output is assembled in EVALUATION format. It copies the secret and drops only trailing towers to match ciphertext size. [Core wrapper][schemeio], [RNS core][decryptcore].
- **I:** Prefer investigating the Poly* scheme Decrypt seam when the intention is to retain configured CKKS polynomial flooding. Do not silently substitute DecryptCore, bind explicitly to PKERNS, or copy the independent test's schoolbook secret decryption into production. Neither low-level path runs the ordinary context wrapper's validation/Decode flow.
- **P:** The client boundary must validate nonnull key/ciphertext/output, populated components, the intended context/key family, ordered bases/roots, prefix relationship and supported component count. A successful DecryptResult return here does not measure slot accuracy. Low-level delegation checks PKE enablement, not all those invariants. [Delegation][schemeio], [prefix use][decryptcore], [wrapper checks][ccdecrypt], [context checks][identity].
- **O/P:** Standard REAL Decode also estimates error, projects/conjugates, adds Gaussian samples and clears imaginary output; a custom high-precision decoder does not automatically retain those measures. Retaining polynomial flooding is not equivalent to retaining every standard output treatment. Keep raw coefficients and high-precision results within the authorized key-holding client; do not expose a decryption oracle or return raw results to the evaluator. The intended client-output policy remains a separate, bounded design decision—not a security proof in this audit. [Standard postprocessing][postprocess], [polynomial flooding][ckksdecrypt].

## 3. Client encoding and the stale Plaintext cache boundary

- **O:** Public Poly construction can allocate zero coefficient storage and expose integer coefficient references. Public DCRT construction from a large Poly reduces every coefficient modulo each supplied limb, preserving that polynomial's format; a COEFFICIENT input is necessary for this interpretation. The ordered ILDCRTParams constructor preserves input order. [Poly allocation][polyctor], [coefficient access][polymutable], [DCRT constructor][dcrtctor], [integer reductions][integercrt], [ordered parameters][orderedq].
- **O:** The inspected dynamic-integer backend has a string constructor and documented base-10 ToString; floating-point conversion functions also exist and must not be used for the lossless integer bridge. This is backend-specific source evidence, not a claim that every configured backend has been compiled or verified. [String input][intin], [decimal output][intout], [floating conversions][intfloat].
- **O:** SchemeBase::Encrypt accepts Element directly. PKERNS Encrypt takes a copy of the DCRT plaintext, uses official EncryptZeroCore, switches its copy to EVALUATION and adds it to the encryption. It returns a ciphertext with key context/tag and noiseScaleDeg=1. It does not call CKKSPackedEncoding::Encode or inspect its cache. [Public entry][schemeio], [RNS encryption][rnsencrypt], [key binding][ctkey].
- **I — Candidate A:** A narrow client encrypt operation could keep exact/multiprecision slots and the coefficient polynomial private, call this Element entry, and return only a validated ciphertext plus necessary public semantics. No stale Plaintext object need escape. Metadata is not automatic on this route: CKKS encoding type, slots, level, noiseScaleDeg and approximate OpenFHE scale must be deliberately assigned consistently; the exact logical scale is separate. Direct scheme output otherwise retains defaults such as INVALID_ENCODING, slots=0 and scale=1. [Defaults][ctdefaults], [ordinary metadata propagation][ccencrypt], [setters][ctmetadata].
- **O/I — Candidate B, only internal:** PlaintextFactory can create a fresh CKKS/DCRT container; GetElement<DCRTPoly>() is mutable. cc->Encrypt consumes that element and copies metadata without calling Encode or checking IsEncoded. This supplies an alternative ephemeral adapter, but its private value cache is empty/old, IsEncoded is separately stored, and public getters cannot represent high-precision values. Do not return it as a coherent high-precision Plaintext, call its standard Encode, or expose its cached getters/printing. No derived “universal plaintext” framework is proposed. [Factory][ptfactory], [state][ptbase], [mutable element][ptmutable], [metadata setters][ptmetadata], [Encrypt][ccencrypt], [cache/getters][cache], [getter types][getter], [Encode cache guard][encode].
- **O:** The current fixture explicitly creates a zero placeholder, replaces only its DCRT polynomial and forbids exposing the cached object as a shipping codec. It is not a production I/O contract. [Current test seam](/Users/lifeng/Documents/20231788-openfhe-codex-precision-01/tests/precision_dcp_rcb_fixture.h:20), [adapter caveat](/Users/lifeng/Documents/20231788-openfhe-codex-precision-01/tests/precision_dcp_rcb_fixture.cpp:258).
- **P:** Validate coefficient rounding, coefficient bounds before reduction, precision budget and complex/REAL convention independently. EncryptZeroCore truncates public-key towers by position, not by matching an arbitrary subset. Only a matching family and supported prefix may be accepted; equal limb counts alone are insufficient. [Public-key prefix logic][encryptprefix].

## 5. What can advance independently of RepeatedMult2

**I — Independently designable now:** lossless client value ingress/egress; the numerical transform/order/rounding contract; integer coefficient access and CRT centering; exact-scale representation; owner-only decryption boundaries; rejection of stale Plaintext exposure; small encode→official Encrypt→official Poly Decrypt→decode acceptance cases on an already approved fixed context. Use a separately derived numerical oracle, including distinctions lost by binary64, signs, near-zero and complex slots. This does not require evaluator secret material or a repeated-multiplication implementation.
**P — Must not freeze yet:** final ordered Q/P/context families, h=128 matching key construction and inter-family secret relationship, public/evaluation-key compatibility, active/raised-basis transitions, per-stage exact physical/logical scales, final pair-vs-RCB output form and eight-squaring precision bounds. Those are the ongoing ordered-Q/RepeatedMult2 design dependencies, not missing features to guess inside I/O.
**O:** Current PaperScaleDescriptor/TensorScaleDescriptor contain approximate long double logical scales, so the existing interface is not an exact rational scale authority. [Current descriptor](/Users/lifeng/Documents/20231788-openfhe-codex-precision-01/include/openfhe_2023_1788/double_ckks.h:24).
**P — Small next evidence gate, not executed:** select one approved context/backend and client output policy; define the narrow I/O contract; red-first numerical and public-I/O tests; then official primitive roundtrip and exact-metadata transport tests on Windows/CI. Keep the independent secret-decryption oracle test-only. Integrate repeated stages only after their family/scale contract is settled. No throughput, leakage or general protocol proof is requested here.
