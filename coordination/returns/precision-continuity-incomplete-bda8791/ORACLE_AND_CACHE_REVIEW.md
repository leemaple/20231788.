# Oracle independence and stale-cache review

## Conclusion

The revised candidate is sufficiently discriminating for the bounded
DCP→RCB tracer bullet, subject to hosted compilation and execution. It does not
use the standard packed double result as a >53-bit expected value, does not use
production RCB as an expected coefficient path, and does not read the stale
packed-value cache after DCRT injection.

## 1. Two deliberately different transform paths

### Fixture path

The green fixture uses a multiprecision port of pinned OpenFHE
`FFTSpecialInv`. It constructs integer coefficients from lossless decimal and
exact-power-of-two inputs and freshly rounds at `2^100`.

Relevant pinned facts:

- the paper defines the CKKS canonical embedding at selected primitive roots and
  encodes by applying the inverse canonical map, scaling and rounding
  (`PAPER-2023-1788.txt:209-219`);
- the pinned rotation group is generated by powers of 5 modulo the cyclotomic
  order (`official-openfhe/dftransform.cpp:50-60`);
- the pinned inverse special transform is
  `official-openfhe/dftransform.cpp:209-239`;
- the packed encoder invokes that inverse before coefficient scaling and
  rounding (`official-openfhe/ckkspackedencoding.cpp:115-133, 191-285`).

### Expected-value path

The contract test does not port `FFTSpecial`. After exact secret/CRT recovery it
uses direct Horner evaluation of the polynomial at 16 explicit roots
`exp(2πi e/128)`, where `e` is an explicit powers-of-five table. No FFT helper is
called on this path.

This separation prevents a shared butterfly, twiddle, bit-reversal or
normalization implementation error from being automatically mirrored.

## 2. Independent worked witnesses

Direct evaluation is itself checked before encryption:

| Witness polynomial | Expected canonical values | Error class rejected |
|---|---|---|
| `2^90` | all `1` | scale, normalization, constant sign |
| `2^90 X^32` | all `+i` | phase direction, conjugation, exponent sign |
| `2^90 X^2` | hard-coded 16-entry decimal table | slot order, powers-of-five order, bit reversal, cyclic shift, sign, conjugation |

The `X^2` expected table is independent decimal data for
`exp(iπe/32)`. It is not generated by either transform implementation at test
runtime.

## 3. Coefficient oracle independence

The test-owned ciphertext oracle:

1. reads the actual RCB output components;
2. converts copies to coefficient format;
3. obtains the actual secret key generated for that trial;
4. evaluates `c0 + c1 s + ...` tower by tower with a project-owned exact
   negacyclic convolution;
5. performs project-owned centered CRT reconstruction using `cpp_int`;
6. evaluates the resulting integer polynomial directly.

This is diagnostic use of the secret key. It is not a proposed production
output path, decryption API or security interface. It avoids production decode
noise/masking only inside the test oracle, not in shipping behavior.

## 4. Why the old inverse-plus-forward pattern was insufficient

If fixture construction and expected decoding both port the same special DFT,
a shared wrong permutation, conjugation, twiddle sign or normalization can
cancel. Agreement would then prove internal consistency rather than agreement
with the canonical embedding.

The revised test breaks that symmetry through:

- an explicit root/exponent table;
- direct polynomial evaluation rather than a forward special FFT;
- independent monomial witnesses;
- a sub-binary64 complex delta checked against exact multiprecision values;
- all-slot non-dyadic, signed and near-zero cases.

## 5. Stale plaintext cache hazard

The pristine plaintext object contains both a polynomial element and derived or
cached packed values. The public API exposes mutable polynomial access
(`official-openfhe/plaintext.h:258-269`) and separately exposes packed-value
getters (`official-openfhe/plaintext.h:366-374`). The green fixture changes the
polynomial after creating a zero placeholder; it does not and cannot, through
the supplied public seam, synchronize the private `complex<double>` cache with
the injected >53-bit source.

The candidate therefore imposes these hard fixture rules:

- never call `GetCKKSPackedValue()` on the injected plaintext;
- never use the placeholder values as expected results;
- never serialize or expose the object as a generally valid packed plaintext;
- use it only as an immediate input to `Encrypt`, whose pinned overload extracts
  `plaintext->GetElement<Element>()`
  (`official-openfhe/cryptocontext.h:1248-1262`);
- keep the adapter in `tests/`, not a production include/source path.

`tools/verify_contract_continuity.py` and the static evidence grep check that the
forbidden getter and standard `context->Decrypt` call are absent from the final
test and fixture.

## 6. Rounding portability review

The prior candidate used a conditional expression combining Boost
`floor`/`ceil` expression-template results. No compiler failure was observed or
claimed. The revised green fixture nevertheless removes an avoidable portability
risk by materializing through explicit branches:

```cpp
BigFloat rounded;
if (value >= 0) {
    rounded = boost::multiprecision::floor(value + BigFloat("0.5"));
}
else {
    rounded = boost::multiprecision::ceil(value - BigFloat("0.5"));
}
return rounded.convert_to<BigInt>();
```

This states half-away-from-zero behavior directly and makes the target type
explicit before conversion to `cpp_int`.

## 7. Remaining limitations

### Requires hosted evidence

- the exact public DCRT construction signatures must compile under pristine
  OpenFHE 1.5.0 on both GCC and MinGW64;
- encryption of the injected element must use the polynomial exactly as pinned
  source inspection indicates;
- all four fresh-key trials must satisfy the predeclared `2^-80` gates;
- warning-as-error behavior must be checked on both toolchains.

### Not covered by this oracle

- production REAL decode masking and its distribution;
- caller-visible high-precision input/output semantics;
- serialization/cache consistency of a production plaintext type;
- Relin2, RS2 or Mult2 error behavior;
- refresh and repeated multiplication;
- security and performance.

## 8. Falsifying checks

The cheapest hosted checks that invalidate this proposal are:

1. patch 0001 does not compile on either pinned host;
2. patch 0001 does not reach an unchanged positive precision assertion because a
   prior state/basis/non-wrap assertion is wrong;
3. patch 0002 changes any file other than the fixture;
4. patch 0002 fails to compile through public DCRT interfaces;
5. the green fixture's independently recovered canonical slots exceed `2^-80`;
6. the hard-coded monomial witnesses fail;
7. any injected-plaintext path reads `GetCKKSPackedValue()` or relies on
   standard double decoding.

None of these should be repaired by relaxing the frozen precision assertions.
They require correction of the fixture, oracle or source assumptions.
